# Stage 9 — content below follows an edited paragraph

Status: verified with real PDFium and the mock, 2026-09-28. Triggered by a user report on Stage 7's
paragraph editing: "글을 추가로 입력하면, 뒤에 문장은 겹쳐 보이는 문제가 있어."

## 1. What was wrong

`edit_paragraph` (Stage 7) deleted the paragraph's objects and laid the new text out downward from the
first baseline, but by its contract nothing else on the page moved. A longer paragraph was therefore drawn
over the lines below it; the UI only showed a toast. While typing, the editor's paper-coloured textarea hid
the text underneath, so the overlap appeared only after 완료.

## 2. What landed

**Engine** (`engine/objects/flow.rs`, new; `paragraph.rs`, `raw/object.rs`, `raw/annot.rs`, `raw/page.rs`)

* `ParagraphEdit.flow`: `push` (default) / `overlap` (Stage 7 behaviour) / `fit`; `ParagraphEdit.dryRun`.
* `ParagraphEditResult` gains `shiftedPt`, `movedObjects`, `movedAnnotations`, `roomPt`, `blocked?`
  (`pageBottom` | `obstacle`) and `fitScale?`. `overflowPt` now means the overlap that *remains* after
  the flow was applied.
* **push**: the content below the paragraph and in its column moves by the change of the paragraph's
  line grid (last baseline − ¼ em, so a descender moves nothing and one more line moves exactly one
  leading). A shorter paragraph pulls the content up. Column membership: horizontal overlap ≥ 60 % of
  the object's width and overhang ≤ 15 % of the column; the column is widened to the body text below when
  the edited paragraph is narrower (block quotes, ragged short paragraphs). Hanging list markers move with
  their item; the paragraph below is moved as a whole (its short last line is not an obstacle).
* **Obstacles** stop the push and never move: objects crossing the column without being in it (full-width
  figures and tables, frames and background boxes that start above the paragraph), AcroForm widgets, and
  the running footer (page number band; detected per column with the *page's* body leading, so a large
  heading does not move it and a signature block above the margin is not mistaken for it). SeePDF
  header/footer stamps are obstacles; watermarks and invisible OCR text are ignored. Content never
  leaves the crop box (`max(crop.b, min(lowest body bottom, crop.b + 18 pt))`).
* **Annotations** in the moved band move with their text: `/Rect` and appearance for every kind, quadpoints
  for text markup (appearance regenerated by PDFium) and links, `/InkList` for ink. Widgets and popups
  never move. Pending 영역 표시 marks in the UI move too.
* **fit**: font size and leading scaled by the largest factor in [0.70, 1.00] (step 0.02) whose line grid
  ends at or above the original bottom; `fitScale` reported.
* **dryRun** computes layout and plan without mutating (generation, undo depth and serialised bytes
  identical; a substitute font is measured in a throwaway document so nothing is embedded).
* One `registry::mutate` → one undo step `undo.paragraphEdit` restores the text and every move.
* Fixed while verifying (pre-existing): a paragraph edit dropped inline images and shading objects
  (`raw/page.rs` rewrite rehearsal now keeps them); on `160F-2019.pdf` any edit moved a superscript onto the
  footnote line; a Hangul-substituted justified line was split by the next probe; justified paragraphs
  with long words re-probed as left-aligned; a SeePDF header stamp next to a paragraph was folded into it.

**UI** (`src/edit/actions.ts`, `TextEditor.tsx`, `EditLayer.tsx`, `redact.ts`, prompts, i18n)

* 완료 runs a `push` dry run. Not blocked → commit with `push`; toast 「아래 내용을 N pt 옮겼습니다 / 당겼습니다」
  with 실행 취소. Blocked → a three-way prompt: 글자 크기 줄여 맞추기 (N %, from a `fit` dry run) ·
  아래로 밀고 남은 부분은 겹치기 · 계속 편집. The prompt names what blocked (page bottom, figure/table,
  running footer, text). With nothing below, the wording says the text runs off the page.
* While typing past the original box: a dashed line at the original bottom and the hint
  「완료하면 아래 내용이 밀립니다」.
* A document change while the prompt is open is detected (stale generation) and the write is never sent
  against the wrong objects; a moved paragraph is found again without remounting the editor, so typed text
  survives. A push refused by the engine keeps the editor open instead of losing the text. Emptying a
  paragraph deletes it and pulls the content up.

## 4. Still open

* **Text / reading order.** The edited paragraph moves to the end of the page's content stream, so
  copying the whole page puts it last. PDFium's content generator writes regenerated objects after the
  ones it did not parse; `FPDFPage_InsertObjectAtIndex` does not change that. Search, selection and
  rendering are unaffected. Fixing it needs our own content-stream rewrite (lopdf) — P2.
* Geometry keys PDFium cannot write (`/L` of Line, `/Vertices` of Polygon, `/CL` of a callout) keep their
  old values when those annotations move; the drawn appearance moves. Popups are not moved.
* Third-party artifacts that are not SeePDF stamps (an Acrobat watermark marked `/Artifact`) are treated as
  content or obstacles.
* A dry run with font substitution measures with the substitute font from a throwaway document; the
  real edit is covered by tests, but the reported `roomPt` can differ by a fraction of a point.
* Every 완료 costs one extra IPC round trip (the dry run), two when blocked.
* Windows QA and Acrobat/Preview checks of edited files are still owed.
