# Spike: text layer, search, selection, text editing, OCR layer, save (pdfium-render 0.9.4)

- Example: `src-tauri/examples/spike_text.rs` — `cd src-tauri && cargo run --example spike_text`
- Library: pdfium-render **0.9.4**, features = default (`pdfium_7881`, `image_025`, `thread_safe`) against
  `libpdfium` chromium/8057 (`src-tauri/resources/pdfium/libpdfium-aarch64-apple-darwin.dylib`),
  bound with `Pdfium::bind_to_library(path)`.
- Outputs (all regenerated by the example, gitignored): `fixtures/out/spike_text_*.{pdf,png}`.
- Timings below are from `cargo run` (dev profile, Apple silicon). pdfium itself is an optimized binary, so FFI
  numbers are representative; the pure-Rust grouping code would be ~10x faster in release.

## 0. TL;DR

| Area | Verdict |
|---|---|
| Per-char geometry (loose/tight boxes, origin, font size/name/weight, colour) | Works. 5,087 chars/page in 6 ms; 14 pages (84k chars) incl. word/line grouping in 79 ms. |
| Search (`FPDFText_FindStart`) | Works. "monkey" over 14 pages: 62 hits in 25 ms (incl. text-page load). Hits come back as **rects only** (no char index). |
| Selection rects from a char range | Works: `segments_subset(start,count)` or union of per-char loose boxes. |
| Coordinate conversion | PDF points, origin bottom-left, y-up, **unrotated user space**. One affine matrix per page (crop box + /Rotate + scale) verified against `FPDF_PageToDevice` for 0° and 90°. |
| In-place `set_text` | Works only if the object's font covers every new glyph. Subset fonts silently drop glyphs (space width 0 → "SeePDFeditedtitle"). |
| translate / scale / font size / delete / add (Helvetica, TrueType) | All work and persist after save/reopen. |
| Korean text | Works with Arial Unicode.ttf / AppleSDGothicNeo.ttc (15 MB / 31 MB embedded per doc!). AppleGothic.ttf renders but extracts spaces as TAB → search breaks. Whole font file is embedded: needs a subsetter. |
| Invisible OCR layer (render mode 3) | Works: extractable + searchable + 0 dark pixels rendered. 1.1 KB doc with Helvetica. |
| Text inside Form XObjects | Readable (search/select OK) but **edits are not persisted**. TAMReview.pdf has 100 % of its text inside XObjects. |
| Save | `FPDF_SaveAsCopy` full rewrite only (no incremental). 1 MB doc in 5 ms. `set_text` alone is **never** auto-regenerated: call `page.regenerate_content()`. |

## 2. Text extraction with geometry (task 1)

tracemonkey.pdf page 1: 612×792 pt, crop box = media box = (0,0)-(612,792).
- `FPDFText_LoadPage` 1.25 ms; 5,087 chars (792 of them pdfium-generated whitespace, `is_generated()==true`, zero-size boxes).
- Per char: loose box (full advance × font ascent/descent: e.g. 'T' `[l=80.52 b=696.92 r=92.48 t=713.04]`), tight box
  (ink: `[l=81.07 b=700.67 r=91.92 t=712.79]`), origin `(80.52, 700.67)` (baseline), `scaled_font_size` 17.93,
  `font_name` "NimbusRomNo9L-Medi", `font_weight` `Weight700Bold`. Collecting all of that for 5,087 chars: **6.2 ms**.
- `segments()` (pdfium's own merged boxes, same baseline + same font): 151 rects on p1 in 36 µs; they coincide with
  the text objects here (one segment per `Tj`). Good enough for a "line" highlight, not for word boxes.
- Word/line grouping (`build_text_layer` in the example): separators = whitespace/generated chars; a new word also
  starts on baseline jump > 0.5 em, horizontal gap > 0.25 em or x going backwards; lines = consecutive words with the
  same baseline (±0.5 em). p1 → 89 lines / 754 words in 0.5 ms (debug). All 14 pages (83,997 chars) including
  grouping: **79 ms** (≈5.6 ms/page). Word rect = union of loose char boxes; line 0 =
  `[l=80.52 b=696.92 r=529.61 t=713.08]` "Trace-based Just-in-Time Type Specialization for Dynamic".
- Char hit test: `chars().get_char_near_point(x, tol_x, y, tol_y)` at the centre of "Trace-based" → char #5 '-'.

Coordinate conversion (verified):
```rust
/// Page -> device affine [a b c d e f]: dx = a*x + c*y + e, dy = b*x + d*y + f.
/// cb = crop box (user space), rotate = page /Rotate (0/90/180/270, clockwise), scale = px per pt.
fn page_to_device_matrix(cb: &PdfRect, rotate_deg: i32, scale: f32) -> [f32; 6] {
    let (cl, cbm, cr, ct) = (cb.left().value, cb.bottom().value, cb.right().value, cb.top().value);
    let s = scale;
    match rotate_deg.rem_euclid(360) {
        90  => [0.0,  s,  s, 0.0, -cbm * s, -cl * s],
        180 => [-s, 0.0, 0.0,  s,  cr * s, -cbm * s],
        270 => [0.0, -s, -s, 0.0,  ct * s,  cr * s],
        _   => [ s, 0.0, 0.0, -s, -cl * s,  ct * s],
    }
}
```
"Trace-based" (chars 0..=10) rect `[80.52, 696.92, 173.82, 713.04]` at 2× → device `x=161.03 y=157.91 w=186.61 h=32.24`;
pdfium `FPDF_PageToDevice` → `(161,158)-(348,190)` ✔ (crop `spike_text_word_crop.png` shows exactly the word).
rotation.pdf p2 (`/Rotate 90`, crop 612×792, display 792×612): first char loose
`[l=90.35 b=72.00 r=103.63 t=79.33]` → mine `(108, 135.5, 11×19.9)`, pdfium `(108,136)-(119,155)` ✔.
180°/270° are derived by symmetry (no fixture). Note `page.width()/height()/page_size()` already return the
**rotated** size, while every char/object box is in unrotated user space — so use the crop box, not `page_size()`, in
the matrix for rotated pages. The frontend should receive this matrix per page and apply it to all rects.

## 3. Search (task 2)

`text.search("monkey", &PdfSearchOptions::new())` per page, `iter(SearchForward)` → each hit is a
`PdfPageTextSegments` (1 rect per line the hit spans; `seg.bounds()`, `seg.text()`):

| options | hits | time, 14 pages (incl. `text()` load per page) |
|---|---|---|
| default (case-insensitive substring) | 62 | 24.8 ms |
| `match_case(true)` | 1 | 16.5 ms |
| `match_whole_word(true)` | 4 | 16.8 ms |

First hit: page 2 `[l=112.58 b=291.65 r=141.91 t=299.72]` "Monkey". `text().all()` for all pages = 25 ms (84k chars);
naive Rust substring search over cached text: 0.2 ms; search over the cached char array of p1 for "trace": 9 hits in 65 µs
**with char indices**. pdfium search results expose no char index (`start`/`count` are private in
`PdfPageTextSegments`), so for a "find → select → replace" flow do the search in Rust over the cached char array
(case folding with `char::to_lowercase`, compare on `char`s not bytes) and use pdfium search only as a cross-check.

## 4. Selection (task 3)

Given char indices `a..=b` (10..=120, spanning 3 lines):
- (a) per-char: iterate `chars.get(i)`, union `loose_bounds()` per baseline run → 3 rects, string built from
  `unicode_char()` (contains the generated `\r\n`); 40 µs.
- (b) `text.segments_subset(a, b-a+1)` → pdfium's `FPDFText_CountRects/GetRect`: 10 rects (splits at every font change,
  e.g. superscript "∗" boxes) — finer than we want for a highlight; merge per line yourself, or use (a).
- (c) `chars_inside_rect(rect)` / `inside_rect(rect)` for drag-rectangles: they are **line-based approximations**
  (char nearest the left-centre → char nearest the right-centre) and `chars_inside_rect` has an off-by-one (returns one
  extra trailing char: `"Trace-"` for the rect of "Trace"). Do rectangle hit-testing yourself against the cached loose boxes.

## 5. Page object model and editing (task 4)

Scan of p1: 151 objects, all `Text`. Per text object: `text_page.for_object(t)`, `bounds()?.to_rect()`, `font().name()/family()/is_embedded()`,
`unscaled_font_size()/scaled_font_size()`, `fill_color()`, `matrix()`, `render_mode()` → **2.3 ms** for 151 objects.
Example: obj#0 "Trace-based Just-in-Time…" rect `[81.07,697.01,529.36,713.08]` font NimbusRomNo9L-Medi (embedded subset)
size 17.93 fill black matrix `[1 0 0 1 80.52 700.67]`. Objects are one `Tj` run each (one line or less).

Char ↔ object mapping (needed to go from a selection to editable objects):
- (A) `t.chars(&text_page)` per object = `chars_for_object`, which scans all chars per object: 47 ms for 151×5,087 (O(objects×chars)).
- (B) per char `c.text_object()` + key `(matrix ×100, font size, for_object text)` → object index: 84 ms, linear.
  Use (B) for object-heavy pages; **never** call `PdfPageTextObject::text()` in a loop (2.28 s for 5,087 calls — it
  loads a text page each time), use `PdfPageText::for_object`.
- Paragraph-like grouping (`group_blocks`): sort by top desc/left asc, merge when x-overlapping and baseline gap ≤ 1.6 em
  → 41 blocks on p1 (title+subtitle = block 0). Good enough for "block" hit-testing; column detection is not needed here.

Conclusions: `.ttc` loads (first face). pdfium embeds the entire font file (Flate-compressed, no subsetting). Glyph
coverage is not checked by pdfium: missing glyphs vanish silently. For Korean, ship an OFL font (Noto Sans KR / Nanum)
and **subset before `load_true_type_from_bytes`**; do not use AppleGothic.

Glyph coverage probing: `font.glyphs().len()` returned **0** for the tracemonkey subset fonts and for built-in Helvetica
(pdfium-render's binary search over `FPDFFont_GetGlyphPath` fails), 65535 for AppleGothic (space: width 3.2, no path;
'한': width 10, 169 segments). So the glyph API cannot be relied on for coverage; use the *trial edit* check instead:
`set_text` → fresh `page.text()` → every char (incl. spaces) must have `loose_bounds().width() > 0`; otherwise revert
or switch to the replace model. `PdfFont::data()` gives the embedded bytes for an offline check with `ttf-parser` (TrueType only; the Type1/CFF subsets in LaTeX PDFs would need another parser).

Form XObjects (`spike_xobject`): tracemonkey has 8 forms with 268 inner text objects, TAMReview.pdf 22 forms with
1,460 inner text objects (its entire content). `set_text` + `translate` on an inner object return `Ok`, in-memory
text/bounds change, `regenerate_content()` returns `Ok`, but after save/reopen **nothing changed** (`FPDFPage_GenerateContent`
only rewrites the page stream, emitting `/Form Do` for the form). Also that font (subset "Cambria", no ToUnicode) extracts
as raw codes `\u{2}\u{3}…` and `set_text` produced "ÿ". Text inside forms is still fully searchable/selectable via `page.text()`.

## 6. Invisible OCR text layer (task 5)

`spike_text_ocr.pdf` (1,126 bytes): grey rect + 3 words with `set_render_mode(PdfPageTextRenderMode::Invisible)` +
one visible control word, Helvetica (non-embedded). Fitting a word to an OCR box: create at (0,0), read
`bounds()` (natural width at font size = box height), `scale(target_w / natural_w, 1.0)`, then
`translate(target.left - natural.left*sx, target.bottom - natural.bottom)`. Fitted rects match the targets to 0.01 pt.
After reopen: `text().all()` = "Invisible OCR\r\nlayer42\r\nVISIBLE control"; `search("ocr")` → 1 hit
`[170,660,220,674.8]`; `char.render_mode()` = `Invisible`; render at 2×: **0 dark pixels** in the invisible box vs 2,480 in the
control box (`spike_text_ocr_crop.png`). Chars keep proper loose boxes, so selection highlights work on OCR text.
For Korean OCR the same approach needs a CID font (see §5 and the LoadCidType2Font note in §8).

## 7. Save (task 6)

- `save_to_bytes()`/`save_to_file()` → `FPDF_SaveAsCopy(doc, writer, flags=0)` (or `FPDF_SaveWithVersion` if
  `set_version` was called). Always a full rewrite: exactly one `startxref` in the output. **No incremental save**
  (`FPDF_INCREMENTAL` exists in pdfium but the flag is hard-coded to 0 in the crate).
- tracemonkey.pdf 1,016,315 B → 996,699 B unmodified (−19.6 KB, pdfium re-serializes) in 5.2 ms; +491 B after adding one
  Helvetica text object on page 4; `regenerate_content()` on an untouched page changes nothing (+0 B).
- `set_text` without `regenerate_content()`: **lost** with `Manual` *and* with the default `AutomaticOnEveryChange`
  (only transforms and add/remove mark the page dirty; `set_text`, `set_render_mode`, `set_fill_color`,
  `set_unscaled_font_size` do not).

## 8. Gotchas (all verified in this spike)

1. `PdfPageTextObject::text()` loads and closes an `FPDF_TEXTPAGE` on every call (0.45 ms). Use `PdfPageText::for_object(&obj)` with one open text page.
2. `set_text` / `set_render_mode` / `set_fill_color` / `set_unscaled_font_size` never trigger content regeneration. Use `Manual` strategy and call `page.regenerate_content()` once before save (6.4 ms for 151 objects). With `AutomaticOnEveryChange` every `translate` regenerates the whole page — avoid for batch edits.
3. `set_text` on subset-embedded fonts silently drops glyphs (space → width 0). `PdfFont::name()` strips the `ABCDEF+` subset tag, `PdfFontGlyphs::len()` is 0 for these fonts, so detection must be the trial-edit check (or replace model).
4. `PdfPage::text()` reflects unsaved in-memory edits (built from page objects), so trial checks work before regeneration. It borrows the page immutably: drop it before `objects_mut()`, reopen after edits.
5. `scale()`/`apply_matrix()` post-multiply in page space → scaling moves the object; anchor with translate(−x,−y)/scale/translate(x,y). `bounds()` of an object is cached until regeneration/reload after `set_unscaled_font_size` (but updates immediately after transforms).
6. Object indices shift after `remove_object_at_index`; the returned object is detached (`text()` returns "") and freed on drop.
7. Text in Form XObjects: readable/searchable, not editable (edits silently not persisted). `PdfPageXObjectFormObject` has no add/remove. To edit, the form must be flattened first (copy children to the page with the form matrix applied, remove the form) — not attempted.
8. Fonts without ToUnicode extract as raw char codes (`\u{2}\u{3}…`, TAMReview) — no usable text, no usable `set_text`.
9. `load_true_type_*(…, is_cid_font=false)` maps code points > 255 to 0xFF ("ÿ"); `is_cid_font=true` with missing glyphs drops them silently. Check cmap coverage of the candidate font first (`ttf-parser`).
10. AppleGothic.ttf: generated ToUnicode maps the space glyph to U+0009 → extracted text has tabs, search for "한글 테스트" fails. Arial Unicode.ttf / AppleSDGothicNeo.ttc are fine but embed 15–31 MB. Whole-file embedding, no subsetting.
11. `FPDFText_LoadCidType2Font` (custom ToUnicode + CIDToGIDMap — the standard way to build a glyphless, language-independent OCR text layer like Tesseract's `pdf.ttf`) is in `PdfiumLibraryBindings` but not wrapped and needs the private document handle → requires a small patch to pdfium-render (`[patch.crates-io] pdfium-render = { git/path = ... }`, ~30 lines in `PdfFonts`).
12. Search hits are rects only (no char index); `chars_inside_rect` is approximate and off by one (+1 trailing char). Run search over the cached char array instead.
13. `PdfRect::new_from_values(bottom, left, top, right)` — unusual argument order. `PdfPageIndex`/`PdfFontGlyphIndex` are `u16`-ish; `pages().len()` iterates fine with `0..len`.
14. Text page `all()` uses `\r\n`; 15 % of chars on a LaTeX page are generated whitespace with zero-size boxes — skip them for boxes, keep them for the string.
15. `page.width()/height()/page_size()` are rotated (display) sizes; char/object boxes are in unrotated user space; build the device matrix from `boundaries().crop()` + `rotation()`.
16. `PdfPageTextObject::new` with an empty string substitutes " " (pdfium crashes on empty text objects); don't create empty objects.
17. Save is a full rewrite; fine at 5 ms/MB but for 100 MB scans expect ~0.5 s and temporary 2× disk usage.

## 9. Recommended editing model

Representation (per page, cached in the engine thread, invalidated on any edit):
- `TextLayer`: `chars[]` (index, unicode, loose box, baseline, font size/name/flags, colour, `object_id`), `words[]`,
  `lines[]` (from `build_text_layer`), plus the page→device matrix. Sent to the UI as flat arrays (`Float32Array`s) —
  ~5 ms/page to build; build lazily per visible page and cache.
- `TextObjectModel`: `objects[]` (page object index, stable key = matrix+size+text, rect, font info, embedded/subset
  status, `editable: bool`, `inside_xobject: bool`), grouped into `blocks[]` (paragraph-like). Char→object via method (B).
- The UI edits *blocks/objects*, never chars: click a block → show its lines as editable text; on commit, apply per line.

Safe edits (in place, always followed by `regenerate_content()`): move (`translate`), resize (`set_unscaled_font_size`
or anchored `scale`), recolour (`set_fill_color`), delete (`remove_object_at_index`), render mode. All persist.

Text content edits:
1. Base-14 font object or fully embedded font that passes the trial coverage check → `set_text` in place.
2. Otherwise **replace model**: new `PdfPageTextObject` with a substitute font (built-in Helvetica/Times/Courier chosen
   from `font_is_serif/fixed_pitch/italic/weight`; for Hangul the bundled subset Korean font), copy matrix + fill colour
   + render mode, `add_text_object`, `remove_object_at_index(old)`. Show a "font substituted" hint in the UI.
3. Multi-line edits: we do the layout ourselves (one object per line, widths from `bounds()`); pdfium has no reflow.
4. Blocks inside Form XObjects → read-only in v1 (badge in UI). Fonts without ToUnicode → read-only.
5. Undo: snapshot `save_to_bytes()` after each committed batch (5 ms/MB) or keep an inverse-op log.

OCR layer: per word, Helvetica invisible text scaled to the word box for Latin; for Korean either (a) patch pdfium-render to
expose `FPDFText_LoadCidType2Font` and use a glyphless CID font with our own ToUnicode (tiny, language-agnostic,
industry standard), or (b) embed one subset Korean font per document (needs a subsetter, ~50–200 KB per doc).
(a) is the better long-term path; (b) works today except for file size.
